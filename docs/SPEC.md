# 仕様書 v0.1

作成日: 2026-10-27 / 設計案。実装・実測で変更した点は理由とともに記録する。

## 1. 目的と成功の定義

自分が登録したチャンネルの動画カードを、自分のPCブラウザ内で非表示にする。どのルールで隠れたかを確認でき、停止すれば元に戻せることを重視する。

「成功」は対象画面と検証条件を限定して報告する。YouTube全体からの排除、推薦アルゴリズムの変更、全端末への反映、視聴履歴や通信の防止を意味しない。自作であることだけを安全性の証拠にせず、コード・権限・データ・通信を確認できる構成にする。

## 2. 対象と段階

| 画面・機能 | 初期の扱い |
|---|---|
| PC版 `www.youtube.com` の検索結果にある通常動画カード | M0/M1の対象 |
| ホームの通常動画カード | M2で実装（v0.2.0）。セル `ytd-rich-item-renderer` 単位。Shorts・ミックス・再生リストは対象外 |
| 動画再生ページの関連・次のおすすめの通常動画カード | M2で実装（v0.3.0、方式2）。プレイヤー・自動再生は操作しない |
| チャンネル検索カード、投稿、コメント、広告、再生リスト、ミックス、複数投稿者のカード | MVP対象外。巻き添えで消さない |
| Shortsのカード・連続再生画面、直接開いた動画、チャンネルページ全体 | チャンネル単位ではブロックしない。v0.6.0のオプション「ショートの棚を非表示」（既定オフ）で、Shortsを含む棚をCSSだけでまるごと隠せる（非表示モードのみ、判定のみでは点線枠、停止で解除）。Shortsの連続再生画面は対象外 |
| スマホアプリ、テレビアプリ、YouTube Music、埋め込みプレイヤー | 対象外 |

WindowsのPC版Chromeを最初の検証対象とする。実際のバージョンは開始時に記録する。Edgeは別途互換性を確認し、Firefox/Safariは初期スコープに含めない。

## 3. 動作モード

| モード | 挙動 |
|---|---|
| 停止 `off` | 拡張が隠した要素を復元し、ページの解析・監視を停止する。設定変更を受け取る最小の処理は残す |
| 判定のみ `observe` | 対象カードを判定し、件数・理由を診断で確認できる。一致カードに赤の実線枠、未判定カードに灰色の点線枠を `outline` で付ける（レイアウト・クリック・再生は変更しない）。2026-10-27変更: 見た目が一切変わらないと判定の有無を利用者が確かめられなかったため |
| 非表示 `hide` | 確認できた登録チャンネルの対象カードだけを隠す |

初回は `observe`。選択したモードとルールは `chrome.storage.local` に保存する。モードはブラウザプロファイル内の共通設定とし、開いている対応タブにも変更を伝える。未対応画面では何もしない。

停止・ルール削除・対象画面からの遷移時に、拡張が付けた非表示状態を戻す。ブラウザの拡張管理画面で拡張そのものを無効化・削除した場合は、ページ再読み込みが復元手段になり得るため、内部の停止スイッチと分けて検証する。

## 4. チャンネルの登録・識別

- 登録画面は日本語。手入力したチャンネルID、ハンドル、対応するYouTubeチャンネルURLを受け付ける。
- 正規化後の識別値と種類を表示し、登録・削除・全体停止ができる。表示名は一覧の目印としてのみ使う。
- URLはプロトコル・ホスト・パスを検証し、動画URLや外部URLをチャンネル登録と誤認しない。
- チャンネルIDを取得できた場合はIDの完全一致を優先する。ハンドルのみならハンドル完全一致のルールとして扱い、改名や情報不足による取りこぼしを表示する。
- 名前の類似、表示名一致、タイトル内の文字列からIDとハンドルの対応を推測しない。
- IDとハンドルは別の識別子である。両者の対応を画面上の同一チャンネルの情報等で確認できたときだけ、その取得元を記録して結び付ける。確認できなければ別ルールのままにする。
- 日本語などを含むURLはURL解析と不正なエンコードの処理をテストする。ハンドルの大文字小文字やUnicode表記を、根拠なく同一視する正規化はしない。
- `/user/`、`/c/` などの旧形式は初期は未対応として説明する。外部APIで自動解決しない。
- チャンネルリンクをカードの投稿者部分から取得する。説明文・タイトル・コメント内にある別チャンネルへのリンクは識別に使わない。
- 識別情報がない、矛盾している、複数投稿者を区別できない場合は `unknown` として残す。誤って隠すより取りこぼしを記録する。

**決定（2026-10-27、M0-01の結果を受けて利用者が選択）:** 識別はDOMのみで行う（方式1）。検索カードのDOMには主に `/@ハンドル` が出るため、ハンドル完全一致が主なルールになる。IDルールは `/channel/UC…` 形式で表示されるカードにだけ一致する。メインワールドからIDを読む方式（方式2）は、方式1の取りこぼしを実測してから再検討する。

**決定（2026-10-28、M2-W01の結果を受けて利用者が選択）:** 再生ページの関連動画はDOMに投稿者リンクがないため、関連動画に限り方式2を採る。メインワールドの `page/owner-bridge.js` が、関連動画セクションのデータの実測経路（RESEARCH.md 7章）から `browseId` と `canonicalBaseUrl` だけを読み、カードの `data-tmf-owner-video/id/handle` 属性に写す。拡張本体（隔離環境）は、属性の動画IDがカードの現在の動画IDと一致するときだけそれを使う。同じデータ項目から得たIDとハンドルは同一チャンネルとして扱い、どちらのルールでも一致させる。経路が見つからない・値が不正な場合は何も書かず、カードは未判定で残る。ページ側スクリプトは chrome API・通信・ページ関数の呼び出しを使わず、拡張が停止中（`<html data-tmf-bridge>` がない）は何もしない。検索・ホームは引き続きDOMのみ。

カード上の登録ボタンはM1の必須条件にしない。**登録の入口（v0.5.0、利用者の判断）:** (1) 設定画面での直接入力（URL・ハンドル・ID）。(2) YouTube自身の「⋮」メニューで利用者が「チャンネルをおすすめに表示しない」または「興味なし」を選んだとき、そのメニューを開いたカードの投稿者を登録する（項目ごとにオン・オフ可、既定は両方オン）。拡張はメニューを開いたり項目を押したりしない。メニュー項目は安定した属性がないため表示文字で見分けるが、投稿者の識別には使わない。追加時は画面下に「取り消す」付きの通知を出す（拡張専用の要素1つ、閉じたShadow DOM）。YouTube側で「元に戻す」を押しても拡張の登録は自動では外れない。v0.4.0で試したホバーボタンは、ホームのプレビュー再生がカードに重なって機能せず、また項目を増やすのは得策でないとの利用者判断で削除した。まず設定画面から登録できればよい。識別可能性を調べる前に大量のルールやUIを作らない。

## 5. 非表示処理

対象カードの単位を画面ごとのアダプターで決める。広い親要素を一括で隠したり、カードをDOMから削除したりしない。拡張専用クラス等とCSSで隠し、通常のレイアウトから除く。

ルールと一致しても、その動画の通信・サムネイル読み込みが既に発生している可能性がある。DOMで隠す方式では、初回の一瞬の表示を完全に防げるとは限らない。対象外カードを含むページ全体の先行非表示でこの問題を隠さず、検証で測る。

初回走査に加え、追加読み込み・属性変更・子要素差し替え・同一ノードの再利用を検出する。再利用で別チャンネルになったカードは再判定して元に戻す。対象カードの「検出」「識別」「ルール判定」「表示変更」を分ける。

`MutationObserver` を使う場合は追加・変更された部分をまとめて処理し、自己変更によるループを避ける。DOMが変わるたびに全ページを走査する実装や、常時の高頻度ポーリングを避ける。SPA遷移では監視対象と集計を整理し、画面固有の非公開イベントだけに依存しない。具体的なDOM構造・遷移の検出方法はM0で確かめる。

## 6. 実装構成と権限

Manifest V3、素のJavaScript・HTML・CSS、実行時の第三者依存なし、ビルド不要を初期方針とする。構成案は次のとおり。現時点では以下のファイルはまだ存在しない。

```text
extension/
  manifest.json
  content/           # 検出、識別、判定、表示変更、診断
  options/           # 日本語設定画面、モードとルール
tests/
  fixtures/          # 個人情報を取り除いた最小DOMと合成例
docs/
local-evidence/      # Git対象外の実測資料
```

静的content scriptの対象は `https://www.youtube.com/*`、トップフレームのみ、実行環境は `ISOLATED`。初期の実行タイミングは `document_start` を候補とし、DOM未構築と設定読み込み中の状態を扱う。設定が読めない間は隠さない。

API権限は `storage` のみを出発点にする。静的注入の `content_scripts.matches` と追加の `host_permissions` は区別し、不要な権限を重ねて宣言しない。`tabs`、`scripting`、Cookie、履歴、ダウンロード、全サイトへの権限、バックグラウンドworkerは必要性が確認されるまで加えない。これらは今回の設計上の選択である。[権限の公式説明](https://developer.chrome.com/docs/extensions/develop/concepts/declare-permissions)

DOMにはアクセスするが、ページの内部JavaScript変数や内部APIを使う設計にはしない（関連動画の読み取りのみ例外、4章の決定を参照）。DOM方式で必要な情報が得られない場合は、その結果を示して次の方式を比較する。[Content scripts](https://developer.chrome.com/docs/extensions/develop/concepts/content-scripts)

## 7. 保存情報と通信

| 情報 | 扱い |
|---|---|
| 設定のschemaVersion、モード、対象画面の設定 | ローカル永続保存 |
| 利用者が登録した識別子、任意の表示ラベル、確認済みの別名と根拠 | ローカル永続保存。自動収集でリストを拡張しない |
| 検出件数、一致・不一致・未判定の件数、処理時間 | ページ単位のメモリ上。既定では永続化しない |
| 診断詳細 | 明示的に診断を有効にした間だけ。件数に上限を設け、動画タイトル・検索語・完全URLを通常ログに残さない |
| Cookie、認証トークン、アカウント識別情報、閲覧履歴 | 読み取り・保存しない |

保存先は `chrome.storage.local`。`storage.sync` やYouTubeページの `localStorage` は使用しない。拡張削除でローカル設定は消えるため、将来必要なら手動の設定入出力を検討する。[Storage API](https://developer.chrome.com/docs/extensions/reference/api/storage)

拡張から外部への `fetch`、XHR、WebSocket、送信ビーコン、外部画像・フォント読み込み、解析SDK、更新用のリモートスクリプトを使わない。ローカルHTTPサーバーも必要としない。ただしYouTube本来の通信は続くため、「ブラウザ全体が通信しない」とは説明しない。

## 8. 再生スキップは後続実験

カードを隠しても、URL直入力・外部リンク・プレイリスト・自動再生から対象動画が再生される可能性がある。M1/M2ではこれを防ぐ機能を実装しない。

M3では、対象動画の投稿者をいつ識別できるか、停止するか移動するか、移動先がない場合、連続した対象動画、戻る操作、音声が先に流れる可能性を調べる。既定OFFの別機能とし、無限スキップや意図しない履歴の増加を避ける方式を、実測後に決める。

## 9. M1の完了条件

- 検索結果の対応する通常動画カードで3モードが動く。
- 登録・削除・再読み込み後の設定保持と、モード変更時の復元が確認できる。
- 非対象のカードを誤って隠さない。識別できないカードは未判定と分かる。
- 追加読み込み・ノード再利用に対する検証結果がある。
- 何件調べて何件に効いたか、何が未検証かを [検証計画](VALIDATION.md) の形式で記録している。
- 実ブラウザ未検証の場合は「実装済み・実サイト未検証」とし、M1の実地確認まで完了したとは書かない。
