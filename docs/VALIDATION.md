# 調査・効果検証計画

状態（2026-10-27）: M0-01の実DOM観察は実施済み（RESEARCH.md 5章）。M1は合成fixtureによる判定テストのみ実施済みで、**実ブラウザでの拡張動作は未実施。** この文書の数値は目標・サンプル計画であり、実測値ではない。

## 1. 何を確かめるか

1. 画面にある情報だけで投稿元チャンネルを識別できるか。
2. 指定チャンネルだけが隠れ、対象外を巻き込まないか。
3. 追加読み込み・画面遷移・DOM再利用で漏れたり、古い判定が残ったりしないか。
4. 停止やルール削除で戻るか。ちらつきや操作の重さはどれくらいか。
5. 拡張自身が追加の外部通信や不要な保存をしていないか。

YouTube側の推薦精度や、長期間の推薦アルゴリズムへの影響を測る実験とは分ける。自作拡張による非表示は、登録ルールとDOM上の結果の対応で検証する。

## 2. M0: 変更前の観察

- ブラウザとバージョン、OS、ページ種別、言語、画面幅、ログイン有無、干渉しそうな既存拡張の有無を記録する。アカウント名やメールは記録しない。
- 検索結果の通常動画カードで、カード境界、投稿者部分のリンク、ID・ハンドルの取得元、データが揃う順番を調べる。
- 登録対象候補と非対象候補を人の目でも確認する。解析コード自身の判定をそのまま正解データにしない。
- 追加読み込みと画面内遷移を観察する。セレクタは取得元と観察日を記録する。
- 識別情報がないカード、Shorts、プレイリスト、広告、複数投稿者の例を区別する。無理に対応扱いにしない。
- 生のページ全体や認証情報を保存せず、必要な最小DOMを匿名化してfixtureにする。再現用に動画の再生を自動で開始しない。

## 3. 同じページでの比較

1. 固定した検索条件で、読み込み済みの通常動画カードをサンプルとして選ぶ。
2. 「判定のみ」でカードの見た目を残し、対象候補とルールの対応を確認する。
3. ページを再読み込みせず「非表示」にする。対象の消失と非対象の残存を確認する。
4. 「停止」に戻して、拡張が隠したカードが戻ることを確認する。
5. 同じサンプルで2〜4を繰り返す。ページ側で内容が差し替わったら同一サンプル比較から外して記録する。
6. 別ケースとして再読み込み、スクロール追加、戻る・進む、ページ内遷移を試す。

ホームは再読み込みで内容が変わり得るため、別時点のスクリーンショットの違いだけで効果を判断しない。動的追加で母集団が変わったら別区間として集計する。

初回パイロットは通常動画カード20件程度、3チャンネル以上、対象・非対象それぞれ5件以上を目安にする。実際にその条件を満たすカードがなければ不足数を報告する。識別失敗の例も記録し、都合のよいカードだけで「全体に有効」と結論しない。

## 4. M1の確認項目

| ID | 条件・操作 | 確認する結果 |
|---|---|---|
| T01 | 初回起動、ルールなし | 判定のみ。動画は隠れない |
| T02 | 対象IDまたはハンドルを登録 | 投稿者情報から一致を判定し、非表示モードだけで対象が消える |
| T03 | 同名・似た名前の別チャンネル | 誤って消えない。合成fixtureでも必ず試す |
| T04 | タイトル等が対象チャンネルに言及 | 投稿者が別なら消えない |
| T05 | 日本語ハンドル、不正URL、旧URL形式 | 対応値は正しく扱い、不明・不正値は誤登録しない |
| T06 | IDだけのルールと、ハンドルしかないカード | 対応関係の証拠がなければ未判定で残る |
| T07 | 無限スクロールでカード追加 | 新規カードも判定され、同じカードを重複集計しない |
| T08 | 同じDOMノードの投稿者・動画が変わる | 再判定し、対象から非対象になれば表示を戻す |
| T09 | 停止・判定のみ・非表示の切り替え | 復元可能。古い状態や監視処理が重複しない |
| T10 | ルール削除・ページ再読み込み・複数タブ | 削除で戻り、保存設定と開いている対応タブの状態が整合する |
| T11 | 検索から対象外画面への遷移、戻る・進む | 対象外に誤適用せず、復帰時に再評価する |
| T12 | 初回表示・リロード・追加カード | 一瞬の表示、空白、スクロール位置の変化を記録する |
| T13 | ID欠落、DOM構造変更、設定読込失敗 | 全体を隠さず、分からない項目を残す |
| T14 | 機能ON/OFFの通信・保存比較 | 拡張由来の追加外部通信がなく、保存が設定と登録ルールに限定される |
| T15 | 拡張管理画面で無効化・削除 | ページ再読み込み後に復元する。内部停止との違いを記録する |

M2では同じ観点をホーム・関連動画に対して別々に実施する。検索で合格したことだけを根拠に対応済みにしない。M3の再生スキップは別のテスト計画を追加する。

## 5. 集計の定義

同一観測区間の読み込み済みサンプルを単位にする。カードのDOMインスタンスとその内容の組み合わせを区別し、再走査回数を件数にしない。ノードが別動画に再利用されたら新しい観測対象にする。SPA遷移では区間を分ける。

- **識別率** = 投稿者を識別できた対象カード数 / 対応種別のカード総数。
- **除去率** = 人が登録対象と確認したカードのうち実際に隠れた数 / 人が登録対象と確認したカード総数。識別できなかった対象も分母に含める。
- **誤非表示数** = 人が非対象と確認したのに隠れた数。初期の受入条件は検証サンプル内で0件。
- **復元数** = 切り替え前に拡張が隠し、同じDOMとして残っているカードのうち、停止後に表示へ戻った数。
- **未判定数** = 投稿者の情報不足・競合等で対象か決められなかった数。名前や表示位置で埋め合わせない。

分母0の比率はN/Aとし、100%と書かない。画面外・未読み込みのカードや、将来出る動画まで含めた保証に広げない。

## 6. ちらつき・性能・通信

「観測できた識別情報が揃った時刻→非表示処理の適用時刻」を計測する。これは描画前に隠せたことの証明にはならない。実際に目に入るちらつきは画面録画やフレーム確認を併用し、行っていなければ未測定とする。

暫定の性能目安は、前景タブで上記遅延の95パーセンタイル100ms以内、主スレッドの1処理バッチ10ms以内。対象PC・サンプル数を添え、測定後に目標自体の妥当性を見直す。追加読み込みのない静止状態で拡張の全件走査やログ出力が続かないことも確認する。

ソース・manifestの確認と、利用できるDevToolsでの通信記録を合わせる。YouTube自身のリクエストと拡張によるリクエストを開始元等で区別する。「host_permissionsがない」「Network欄が空だった」だけで通信なしと断定しない。確認したコンテキストと観測時間を記録する。
